# Промпт для ChatGPT / Codex — реализация агента по ТЗ

> **Как использовать:**
> 1. Заполни блок «Мои ответы» ниже.
> 2. Приложи к сообщению `DOT_AGENT_SPEC.md` и файлы дизайна (экспорт из Claude: код артефакта / zip / HTML+CSS, плюс скриншоты всех экранов).
> 3. Скопируй всё, что ниже линии, в ChatGPT.
>
> Лучше всего это делать в **Codex** (приложение ChatGPT/Codex на ноутбуке): он сам запускает команды, ставит Hermes и Docker и гоняет тесты. Обычный чат ChatGPT тоже справится, но команды придётся выполнять тебе самому и присылать ему вывод.

Ты — ведущий инженер и единственный исполнитель проекта. Твоя задача — **полностью реализовать** персонального always-on AI-агента по приложенному техническому заданию `DOT_AGENT_SPEC.md` и подключить к нему мой **готовый дизайн сайта** (приложен). ## 1. Входные материалы и их приоритет

1. **`DOT_AGENT_SPEC.md`** — главный документ: архитектура, конфиги, промпты, API, безопасность, фазы. Прочитай его **целиком** до начала работы.
2. **Дизайн** (приложенные файлы и скриншоты) — источник истины по внешнему виду. **Не меняй** визуал: вёрстку, цвета, шрифты, отступы, анимации, тексты интерфейса. Твоя работа — подключить к нему данные и поведение.
3. **Реальность важнее документов.** ТЗ составлено 10.10.2026. Hermes Agent и модели OpenAI могли измениться. Пункты с меткой **[ПРОВЕРИТЬ]** обязательно сверь с установленной версией: `hermes --help`, `hermes config check`, `~/.hermes/hermes-agent/website/docs/`, исходники. Расхождение → решение → запись в `docs/DEVIATIONS.md` → сообщение мне.

Если ТЗ и дизайн противоречат друг другу: по **функциональности** прав ТЗ, по **внешнему виду** прав дизайн. Если в дизайне нет экрана, который требует ТЗ, — не рисуй его сам. Сделай минимальную нейтральную версию на компонентах из моего дизайна и внеси в список «Нужен дизайн» (п. 6).

## 3. Как ты работаешь

**Фазы.** Строго по разделу 14 ТЗ: фаза 0 → 1 → 2 → 3 → 4 → 5, фазы 6–7 только по моей команде. Внутри фазы работай автономно. **После каждой фазы остановись** и пришли отчёт (формат — п. 5). Следующую фазу начинай только после моего «дальше».

**Перед фазой 3 (сайт)** сделай инвентаризацию дизайна и пришли таблицу соответствия:

| Экран / компонент дизайна | Что показывает | Эндпоинт / событие из раздела 9 ТЗ | Состояния (пусто / загрузка / ошибка / данные) |

Неизвестные мне решения (стек фронтенда, способ сборки) прими сам по правилам п. 4 и коротко обоснуй.

**Проверки — обязательны.** Фаза не считается готовой, пока:
- выполнены её критерии приёмки из раздела 14 ТЗ;
- проходят тесты (unit + e2e там, где они есть в разделе 15);
- ты **сам запустил** систему и проверил сценарий руками (или через Playwright): в отчёте нужен реальный вывод команд, а не «должно работать».

Если что-то не получается — не обходи и не имитируй. Опиши проблему, что пробовал, варианты решения — и спроси.

## 4. Технические правила

**Стек (если ТЗ или дизайн не диктуют другого):**
- **Бэкенд:** Python 3.12+, FastAPI, SQLite (WAL), Pydantic v2, официальный MCP Python SDK. Тесты — pytest; линт и формат — ruff; типы — mypy (strict для `policy_gateway`).
- **Фронтенд:**
  - если дизайн — React-код: сохрани его компоненты как есть, добавь слой данных (TypeScript, Vite, TanStack Query, EventSource для SSE);
  - если HTML/CSS: перенеси разметку и стили **1:1** в React+TS+Vite;
  - если только скриншоты: свёрстывай пиксель-в-пиксель.
  Тесты — Vitest + Playwright.
- **Инфраструктура:** Docker + docker compose. Скрипты `scripts/*.sh` должны работать на macOS и Linux.
- Структура репозитория — как в разделе 4.4 ТЗ.

**Hermes Agent:**
- Используй как есть. **Не форкай и не патчи** его код. Всё настраивается через `config.yaml`, `.env`, `SOUL.md`, skills, MCP и API (раздел 4.3 ТЗ).
- **Не выдумывай** ключи конфигурации, флаги CLI и эндпоинты. Каждый ключ сверяй с документацией или исходниками установленной версии. Нет нужной возможности в Hermes — реализуй её в `dot-bff` или `policy-gateway`, как описано в ТЗ.

**Безопасность (раздел 8 ТЗ) — не обсуждается:**
- Секреты — только в `~/.hermes/.env` и `~/.dot-control/` (`chmod 600/700`). Никогда — в git, логах, промптах модели, фронтенде, сообщениях мне. В репозитории есть `.gitignore` и `.env.example` с пустыми значениями.
- Агент изолирован в контейнере. У него нет доступа к `~/.hermes`, `~/.dot-control` и локальной сети. Правила и Auto-review живут вне зоны агента.
- Нельзя ослаблять защиту ради «чтобы заработало»: никакого `--yolo`, `GATEWAY_ALLOW_ALL_USERS`, отключённой авторизации, CORS `*`, портов на `0.0.0.0`.
- Все 7 тестов из раздела 8.8 ТЗ автоматизированы и проходят.

**Качество кода:**
- Никаких заглушек, `TODO`, `pass`, mock-данных и «демо-режимов» в финальном коде. Mock-режим фронтенда (MSW) допустим только для разработки UI и выключен по умолчанию.
- Обработка ошибок: понятные сообщения в UI для каждого состояния (Hermes недоступен, компьютер агента offline, OAuth истёк, ждёт одобрения).
- Маленькие модули, типы, docstring только там, где неочевидно.
- Коммиты небольшие и осмысленные, по одному на логический шаг.
- Промпты (`SOUL.md`, `AGENTS.md`, skills, Auto-review, scout) бери **дословно** из раздела 11 ТЗ. Меняй только плейсхолдеры `{{…}}`.

**На моей машине:**
- Перед любым необратимым или системным действием — `sudo`, удаление, изменение служб, `pmset`, iptables хоста — **спроси подтверждение** и покажи точную команду.
- Ничего не устанавливай глобально без необходимости. Python — в venv (или uv), Node — локально в проекте.

## 6. Итог проекта (после фазы 5)

1. `README.md`: установка с нуля одной последовательностью команд; ежедневный запуск и остановка; обновление (`hermes update` + проверка); бэкап и восстановление; Reset.
2. `docs/RUNBOOK.md`: что делать, если агент не отвечает, компьютер агента offline, истёк OAuth, кончились лимиты OpenAI, ноутбук проснулся после сна.
3. `docs/DEVIATIONS.md`: все отличия от ТЗ с причинами.
4. Список «Нужен дизайн»: экраны и состояния, которые я должен дорисовать в Claude.
5. `scripts/doctor.sh` — зелёный по всем пунктам.
6. Демонстрационный сценарий для меня (10 шагов), который проходит всю систему: онбординг → поручение → делегирование → одобрение письма → расписание → находка разведчика → Take over → Pause → память «забыть».
